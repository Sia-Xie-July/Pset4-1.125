Before the Merge is a three-part series for technical leads of 3–10-person software teams deciding how much work to delegate to coding agents.

In the first piece we looked at how practitioners are structuring agent work. This piece asks a harder question: what kind of evidence would justify believing that those structures save a team effort? Our argument is that three things must be kept apart: a description of what a tool or workflow does, a commercial performance claim, and a measured outcome for a team. This month's material about agents checking their own work contains the first two. It does not contain the third. Treating them as interchangeable makes an adoption decision harder to defend.

Practitioner framing: control, not model choice

The HTML All The Things podcast opened its 13 October episode, AI Basics For Developers, with a deliberately unglamorous point. In the first forty-seven seconds, the hosts say the hard part is not figuring out which model is the smartest, but learning to work with these tools without giving up control of the codebase. [02-c1]

That is useful framing. It names the integration problem a technical lead actually faces. It is not a productivity study, and we should not cite it as one.

A sponsor's number

The 12 October episode of The AI Daily Brief, How to Go from AI Power User to AI Leader, carries an advertisement for Blitzy at around twenty-two minutes. The ad describes reverse engineering a codebase into a knowledge graph and claims the product delivers over 80% of entire software epics autonomously, validated and end-to-end tested. [02-c2] That figure is a sponsor's claim inside a paid read. This project has not verified it, and the host is not the source of it.

Before letting a number like that shape a decision, ask what the denominator is. How were the epics selected? What counted as complete? How much human planning, review and correction remained afterwards? Were failed attempts included? The passage answers none of these questions. That does not prove the product cannot help. It means the excerpt cannot establish the size of the benefit for a team like yours.

A workflow description with real tests

The most concrete material comes from Jake Cukjati's AIMUG talk. Between roughly six minutes sixteen seconds and six fifty-four, he describes working with one agent at a time, then using a test-harness plugin so the agents check completed specs, with a checklist for integration testing and end-to-end tests. [02-c3]

This is more specific about process than a broad promise of autonomy, and it is the kind of practice a small team can copy. But a description of testing still does not measure review burden, rework or defects after deployment. It tells us where checks happen, not what they save.

Different evidence, not triple confirmation

It would be easy to read these three sources as agreement that agents can now verify their own work. They are not three confirmations of one productivity result. They are three different kinds of evidence: a practitioner concern about control, a promotional performance claim and a workflow description. None measures review time, rework or post-release defects. [02-c4]

Our synthesis is that a team should ask where verification work goes, not just whether an agent performs a verification step. Work can move from writing code to specifying tasks, interpreting test output and correcting plausible-looking mistakes. If the agent writes the tests as well as the code, a reviewer must also judge whether the tests ask the right questions. That is the sense in which review can become the bottleneck: the checking does not vanish, it concentrates.

What a defensible claim would need

A practical scorecard would count human time across the whole task, not just time to first draft; the share of agent changes accepted without major rework; the rework that was needed; and defects found later. It would keep the task boundary clear and compare against a reasonable baseline of similar work. These are evaluation suggestions, not measurements made in this series.

Limitations

We reviewed selected passages, not a complete empirical survey. Missing measurements here do not show that coding agents are ineffective, and one team's pilot will not settle the question for every organisation. The title's review-bottleneck framing is a question we are posing, not a finding the sources establish. The defensible conclusion is narrower: these excerpts explain practices and promises, but none independently quantifies a delivery improvement. The next piece turns these questions into a small, reversible evaluation plan.
